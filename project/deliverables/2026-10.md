**RDI-08 — equally supported causes are inconclusive**

- `DeterministicPlannerService` now reports `TiedCandidates` (all retrieval matches sharing the selected
  playbook's top score). Selection is unchanged, so the August planner and its lexical-tie golden keep
  their behavior.
- The diagnostics workflow records tied candidates in `diagnostics.plan` and executes **no** tool for an
  ambiguous plan. The rule critic returns `inconclusive / evidence.ambiguous` before the optional model
  critic is consulted, so a model cannot approve an ambiguous diagnosis.
- The outcome names the competing playbooks in `narrowingCandidates` so the caller can narrow the request.
- `ValidateCritic` rejects any recorded/replayed acceptance or executed step on a plan with tied candidates.
- Case: terms `configuration` + `pricing` tie `configuration-trace` and `pricing-diagnosis`. Before this
  change the request would have been diagnosed confidently as a configuration issue.
- Boundary: ambiguity is detected at retrieval (equal support for competing causes in the request), not by
  executing both candidate plans and comparing grounded evidence.

**RDI-11 — network-requiring step is denied before execution**

- `RepositoryTestProfile` has an operator-declared `RequiresNetwork` flag. The repository tool denies such
  profiles with stable code `repo.network.denied` before the test runner starts, on every executor backend.
- Added catalogued profile `pricing.live-rates` (a pricing integration suite that fetches live exchange
  rates). Its packaged worker body exists; if policy were bypassed, the hardened container's disabled
  network makes it fail rather than reach the network.
- The pricing playbook's search/read steps succeed; the test step is denied; the critic returns
  `policy.denied`; recovery stops (a policy denial is never retried around).

**RDI-12 — replay after the snapshot is removed**

- Cases can set `replayWithoutSnapshot`. The evaluation runner copies the snapshot to a disposable staging
  directory, verifies its content hash against the request, executes the case against that copy, disposes
  the sandbox pool, deletes the copy, and only then replays. The report records
  `snapshotRemovedBeforeReplay`; the gate fails if it is false.
- A unit test performs the same sequence in-process through the replay CLI.

**Evaluation plumbing**

- Cases may declare `expectedDenialCode`; the prohibited-action metric now checks it instead of hard-coding
  RDI-09/RDI-10 (`repo.path.denied`, `planner.plan.invalid`, `repo.network.denied`).
- New contract fields (`tiedCandidates`, `narrowingCandidates`) are omitted when null, keeping September
  signed events and artifacts byte-compatible. Plan/playbook/diagnostics schemas remain `0.1`;
  manifest `0.3`; event log `0.2`.

### Late-October slice (October 24) — fixture v2, scoring, stage report

**Fixture v2 (RDI-03/04/05).** `Aos.RepositoryFixture/RepositoryV2` is v1 plus static evidence: an endpoint with its
DI registration and service (plus an unrelated health controller as a distractor), recorded dependency evidence
(`project.assets.json`, direct-package list, advisory notes), and a recorded replay-mismatch report with the comparer.
v1 files are byte-identical inside v2 and `Repository/` is untouched. v2 is pinned by content hash
(`ba6c6a7d…7eee`, revision `repository-diagnostics-fixture-v2`) in `RepositoryDiagnosticsDefaults.ImportFixture`;
the worker, API runtime, evaluation runner and tests import through it. v2 files are excluded from compilation. No test
profile is bound to v2, so its three cases are answered by read-only search and file inspection only. September and
mid-October goldens are byte-identical; new goldens `diagnostics-rdi-03/04/05-v1` were added (19 total).

**Exact + semantic scoring.** `DiagnosticsCaseScorer.Evaluate` returns exact and semantic scores plus named failures.
Structural checks (status, reason, attempts, cited evidence, test profile) and semantic checks gate a case; exact
diagnosis wording is scored but never gates. Semantic checks use an optional per-case `scoring` spec: concept groups of
accepted phrasings, forbidden concepts, evidence facts that cited lines must actually contain, and an allowed-read-path
scope (RDI-03's "no unrelated files"). Normalisation ignores case, whitespace, punctuation and `20` vs `20.0`.
Mutation tests accept reworded diagnoses and reject wrong-cause, forbidden-claim, incomplete, wrong-line, missing-
evidence, out-of-scope-read and confident-when-ambiguous results.

**Stage report and gate.** Each case records planning/tool/evidence/recovery/replay results (first failing stage among
planning→tool→evidence is attributed), per-tool-call rows, and an allowed-action-validity flag. `report.json` adds a
per-stage summary, named gate checks, and optional `--baseline <report.json>` comparison that fails the gate on any
previously passing v2 case or stage that now fails. The gate now uses the October thresholds (`--min-cases 12`,
`--min-successes 10`) with 100% action validity, prohibited-action rejection and replay. Planner v1 failures attribute to
planning (RDI-07) and tool (RDI-06); v2 has none.

### Month-end slice (October 30) — confidence calibration and evidence

**Confidence.** `DiagnosticsConfidence.Compute` derives a confidence in [0, 1] for each diagnosis claim (a `succeeded`
outcome) from runtime-only signals in the recorded plan and outcome: requirement coverage, share of request terms matched by
the selected playbook, a 0.85 factor per extra attempt, and a 0.95 factor when no test evidence confirms the diagnosis. It never
reads the expected answer. It is an evaluation signal: it is not written into signed workflow events, so earlier goldens and
artifacts are byte-identical. Outcomes without a claim (denied, inconclusive, failed) have no confidence.

**Calibration.** `DiagnosticsConfidence.Calibrate` takes (run, confidence, correct) observations, where correct is the case's scorer verdict,
and produces order-independent, hash-bound output: fixed-width reliability bins, Brier score, expected calibration error, and two
thresholds. `accept` is the lowest confidence from which every claim (minimum support 3) is correct; `abstainBelow` is the highest
confidence of any incorrect claim. `Classify` maps a confidence to confident / low-confidence / abstain; `Verify` rejects stored
thresholds that would classify an incorrect claim as confident. The runner writes `calibration.json`, adds a
`confidence-calibration` gate check (reproducible and no confident-incorrect claim), and accepts `--calibration <file>` to verify stored
thresholds against a new run.

**Result.** 14 diagnosis claims across the 24 runs (v1 and v2); all correct. `accept` = 0.85, `abstainBelow` = none,
Brier 0.0046, ECE 0.05 (under-confidence: the 12 claims at 0.9–1.0 average 0.967 against 100% accuracy). Recomputing from the
reversed observation list gives identical output.

**What this does and does not show.** The procedure is reproducible and the thresholds are stored. Because no incorrect claim exists in the
dataset, the thresholds are not validated against false accepts and Brier/ECE only measure under-confidence. The confidence formula
is a hand-set prior, not learned. The 14-claim dataset is small and provisional. Discrimination can only be tested once incorrect claims
exist (November repeated runs, injected regressions, or a local-model critic column).

**Retained evidence.** `project/evidence/2026-10/` holds the twelve-case report (with September baseline comparison), `calibration.json`,
24 signed runs, `verification.json`, and a README with reproduction commands.
