## 2026-08 status

August 2026 work for Planner v1: playbooks, deterministic retrieval, constrained plans, and step execution.

### 2026-08 starting point

- July closed with capability-protected sandbox execution, deterministic tool-outcome replay, and a two-scenario golden evaluation set.
- The April local-model spike showed that raw planner output was not reliable enough to trust: it violated requested formats, hallucinated repository structure, and drifted away from the .NET architecture.
- Manifest schema `0.3` and event-log schema `0.2` did not contain planner artifacts.
- No playbook store, constrained plan contract, or planner validator existed.

### 2026-08 update (1/2 DONE)

Implemented the deterministic planner foundation before model generation or step execution:

- Added separate versioned planner contracts:
  - plan schema `0.1`
  - playbook schema `0.1`
  - ordered plan steps with explicit ids, action ids, and arguments
  - allowed-action definitions bound to a concrete tool id/version and argument allow-list
  - playbook step templates and explicit retrieval terms
- Added a fail-closed `PlannerPlanValidator`:
  - rejects unsupported plan schema versions
  - requires plan identity, task class, and at least one step
  - requires contiguous one-based step ordering
  - rejects duplicate step ids
  - matches action ids using ordinal, case-sensitive comparison
  - rejects actions and arguments not present in the allowed-action catalogue
  - enforces required action arguments
  - returns stable machine-readable error codes and paths
- Added `IPlaybookStore` and `InMemoryPlaybookStore`:
  - validates playbook schema and required fields at startup
  - rejects duplicate playbook id/version pairs
  - snapshots mutable input collections
  - normalizes retrieval terms using trim + invariant lowercase
  - returns playbooks in stable task-class/id/version order
- Added `DeterministicPlaybookRetriever`:
  - exact ordinal task-class filtering
  - exact normalized retrieval-term overlap scoring
  - score-descending ranking
  - lexical playbook-id/version tie-breaking
  - query/store input order does not affect results
  - zero-overlap candidates are excluded when query terms are supplied
- Added focused tests for plan validation, fail-closed action matching, deterministic error ordering, retrieval ranking, order independence, result limits, store snapshots, duplicate identities, and unsupported schemas.

### August 2/2 closure scenarios

The end-of-month vertical slice will include at least these five successful scenarios:

1. Exact task-class and term retrieval produces and executes a one-step plan.
2. A two-step plan executes strictly in sequence and records both outcomes.
3. Multiple playbooks with different overlap scores select the highest-scoring playbook and execute its plan.
4. Equally scored playbooks use the lexical tie-break and execute the same selected plan regardless of input order.
5. A plan using both required and optional allowed arguments reaches the capability-protected tool executor successfully.

Negative coverage remains additional to the five successful scenarios:

- unsupported or malformed plan schema
- unknown action or argument
- capability denial
- sandbox timeout/failure
- local-model output that cannot be parsed or validated
